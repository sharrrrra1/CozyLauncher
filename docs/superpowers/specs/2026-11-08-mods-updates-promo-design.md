## 1. Что строим

Четыре блока в одной spec, потому что они используют одни и те же механизмы:

1. **Каталог модов** с Modrinth: поиск, фильтр по версиям Minecraft, которые уже установлены в лаунчере, установка в выбранную версию.
2. **Автозависимости**: если мод требует другой мод, лаунчер скачивает его сам и показывает, что именно и зачем он скачивает.
3. **Промо CozyPOLIT** — удалённо управляемый блок (сервер ещё не открыт) плюс рабочая кнопка «Играть на сервере».
4. **Автообновления лаунчера** через GitHub Releases, чтобы публичная сборка обновлялась сама и не требовала переустановки.

Дополнительно, как следствие: установка готовых сборок модов (`.mrpack`), обновления модов и лоадера в один клик, включение/выключение мода без удаления, проверка нехватки зависимостей до запуска игры.

## 3. Проверенные факты (не пересказ документации)

Проверено живыми запросами 2026-11-08. Реализация обязана опираться на это, а не на ожидания:

- **Fabric не отдаёт готовый version JSON.** `GET /v2/versions/loader/1.21.4/0.20.1/1.1.2/profile` → `404`, эндпоинта нет. Профиль синтезируем сами.
- Рабочий эндпоинт: `GET https://meta.fabricmc.net/v2/versions/loader/{mcVersion}/{loaderVersion}` → `{ loader, intermediary, launcherMeta }`.
- В `launcherMeta.libraries.common` лежат **только** `org.ow2.asm:*` (×5) и `net.fabricmc:sponge-mixin`. **`fabric-loader` и `intermediary` там отсутствуют** — их надо добавлять самому из `loader.maven` (`net.fabricmc:fabric-loader:0.20.1`) и `intermediary.maven` (`net.fabricmc:intermediary:1.21.4`). Оба jar проверены: `https://maven.fabricmc.net/...` → `200`.
- `launcherMeta.mainClass.client` = `net.fabricmc.loader.impl.launch.knot.KnotClient`, `client` в `libraries` пустой.
- **Modrinth требует фильтра в теле запроса**: `/v2/project/{slug}/version?game_versions=["1.21.4"]&loaders=["fabric"]` → массив версий. У каждой: `id`, `name`, `files[].url` (cdn.modrinth.com), `files[].hashes` = **hex** `sha1` + `sha512`, `files[].size`, `dependencies[]`.
- **`dependencies[].version_id` почти всегда `null`** (проверено на `modmenu`: два `required`), поэтому зависимость разрешается по `project_id` + тому же фильтру `game_versions`/`loaders`, берётся новейшая.
- В ответе `/v2/search` есть `icon_url` (cdn.modrinth.com), `title`, `description`, `categories`, `downloads`, `client_side`, `server_side`, `date_created`/`date_modified`. **`date_published` в поиске нет** — не на что опираться.
- **`.mrpack` — zip с файлом `modrinth.index.json`** (не `modrinth.manifest.json`), плюс `overrides/`. Ключи: `formatVersion`, `game`, `versionId`, `name`, `files`, `dependencies`. Реальный пример Fabulously Optimized 8.2.0: файл 182 799 Б, 48 файлов, `dependencies: {"fabric-loader":"0.19.3","minecraft":"1.21.4"}`, у файлов есть `path`, `hashes`, `env{client,server}`, `downloads`, `fileSize`; среди путей есть не-jar (`resourcepacks/*.zip`), в `overrides/` — `config/*.json5` и др. Полей `gameVersions`/`loaders` в реальном паке нет.

## 4. Модель данных и главная правка ядра

### 4.1 Разрешение версии с родителем

Fabric-профиль — это обычный version JSON с `inheritsFrom`. Сейчас `getVersionJson()` ([mojang.ts:104](../../../src/main/core/mojang.ts)) читает только манифест Mojang, поэтому локальные версии для него невидимы.

Новый порядок разрешения идентификатора:

1. Если в `<gameDir>/versions/<id>/<id>.json` есть файл — читаем его (локальная версия).
2. Если в нём есть `inheritsFrom` — рекурсивно разрешаем родителя, затем сливаем:
   - `mainClass`, `arguments`, `libraries` — из ребёнка (библиотеки конкатенируются, ребёнок идёт последним);
   - `downloads.client`, `assetIndex`, `assets`, `javaVersion`, `logging`, `releaseTime`, `type` — из родителя, если ребёнок их не задаёт;
   - `id` остаётся детским.
3. Иначе — как сейчас: манифест Mojang + кэш в `cache/versions`.

Цикл в `inheritsFrom` запрещён: глубина ≤ 4, множество посещённых id, иначе ошибка.

Идентификатор модовой версии: `1.21.4-fabric-loader-0.20.1` (символы только из разрешающего regex `installer.ts:30`; знак `+` в него не входит, поэтому имя строим сами, а не копируем из Modrinth).

### 4.2 Где живут файлы

| Что | Куда | Комментарий |
|---|---|---|
| Манифест модовой версии | `<gameDir>/versions/<modId>/<modId>.json` | синтезируемый, с `inheritsFrom` |
| Клиент-jar | **не дублируется**, берётся из родительской версии | экономия ~500 МБ на версию |
| Библиотеки Fabric | `<gameDir>/libraries/<maven path>` | общий каталог, sha1-проверка существующим загрузчиком |
| Моды | `<gameDir>/versions/<modId>/run/mods/` | run-папка, см. ниже |
| Миры, конфиги, `options.txt` модовой версии | `<gameDir>/versions/<modId>/run/` | изоляция наборов модов |
| Установленные моды (метаданные) | `<launcherData>/mods-index.json` | что, какой версией, откуда, хеши |
| Промо-состояние и кэш | `<launcherData>/news-cache.json` | только кэш |

**Ключевое решение:** ванильная версия запускается ровно как сегодня — рабочая папка `<gameDir>`, существующие миры и настройки не трогаются. Модовая версия получает свою run-папку, потому что Fabric loader читает `<gameDir>/mods`, и два разных набора модов иначе перемешались бы. Тяжёлые `libraries/` и `assets/` при этом не копируются: они остаются общими и передаются явно — `library_directory` и `assets_root` в `vars` уже так и делают ([launcher.ts:156](../../../src/main/core/launcher.ts)).

Отдельный пользовательский слой «инстансы» сознательно **не** вводим: run-папка версии даёт изоляцию бесплатно, а UI инстансов — это отдельный цикл, если понадобится.

### 4.3 Что меняется в запуске

`GameLauncher.launch()` принимает тот же `versionId`, но:

- рабочая папка = run-папка, если версия модовая; создаётся до запуска вместе с `mods/`;
- `verifyInstall` для модовой версии проверяет родителя, библиотеки лоадера и наличие файлов модов, а не собственный клиент-jar;
- в `buildGameArgs` добавляется `options.extraGameArgs` по образцу уже работающего `--fullscreen` ([args.ts:85](../../../src/main/core/args.ts)). Только через него передаются `--server`/`--port`, и значения проходят валидацию (§8).

## 5. Каталог и установка модов

Весь сетевой код — в основном процессе. В собранном виде стоит CSP `connect-src 'self'` ([index.ts:116](../../../src/main/index.ts)), поэтому запросы из рендерера блокированы политикой, а не случайностью; UI получает данные через IPC.

Новые модули: `src/main/core/mods/{modrinth,resolve,deps,installed,install,pack}.ts`, `src/main/core/fabric.ts`, `src/main/core/promo.ts`, `src/main/core/updater.ts`.

### 5.1 Клиент Modrinth

- User-Agent вида `CozyLauncher/<версия> (+https://github.com/sharrrrra1/CozyLauncher)` — сервис просит опознаваемое приложение.
- Кэш ответов TTL 10 минут по образцу `MANIFEST_TTL` в `mojang.ts` + disk-cache в `cache/mods/`, чтобы при офлайне каталог не был пустым.
- Таймаут 15 с, одна повторная попытка, очередь: не более 4 одновременных запросов.
- Иконки модов. **Важно:** `img-src 'self' data:` не пустит удалённые картинки, поэтому main качает иконку сам и отдаёт в UI как `data:` URI (тот же приём, что уже работает для спрайтов и скинов). Нет иконки — локальный спрайт `McSprite` (зелье/алмаз), а не битая картинка.
- Только `https://api.modrinth.com` и `https://cdn.modrinth.com`: любой URL вне этого списка отклоняется до запроса.

### 5.2 Поиск и выбор версии

Фильтр жёстко привязан к установленным версиям: список берётся из `getVersionStatuses()` ([installer.ts:167](../../../src/main/core/installer.ts)), и в каталоге доступны только те `game_versions`, которые уже скачаны. Facets: `project_type:mod`, `categories:fabric`, `versions:<mc>`.

### 5.3 Разрешение зависимостей (то, что просил владелец)

Пошагово: замыкание по обязательным зависимостям.

- Старт: выбранный мод. Шаг: для каждой `dependencies[]` — `required` → резолвим по `project_id` через фильтр §5.2 и берём новейшую версию; `optional` → предлагаем галочкой, по умолчанию выключено; `incompatible` → не качаем, а **блокируем установку** и объясняем конфликт; `embedded` → пропускаем (зашит в jar).
- Порядок обхода — в ширину. Дедупликация **по `project_id` на входе и по `id` версии после резолва**; полагаться на `dependencies[].version_id` нельзя — он `null` (§3). Повторный визит к уже взятой версии = цикл, тихо пропускаем.
- Потолок: 60 файлов и 400 МБ. Превышение — явная ошибка, а не бесконечная докачка.
- **Превью до скачивания**: список «что и почему» и итог по размеру («будет скачано 7 файлов, 41 МБ»). Без согласия не качаем ничего.
- Каждый скачанный файл сверяется по **sha1 и sha512** из API. Текущий `downloader.ts:74` умеет только sha1 — добавляется поле `sha512`, логика не переписывается.
- Отмена и прогресс — через существующий `AbortController` + канал `mods:progress` в формате `InstallProgress`.

### 5.4 Установка

1. Убедиться, что родительская ванильная версия установлена, иначе — предложить докачать.
2. Синтезировать профиль Fabric (§3) и записать `<modId>.json`.
3. Скачать библиотеки лоадера (включая `fabric-loader` и `intermediary`, которых нет в `launcherMeta`) с проверкой sha1.
4. Скачать моды и зависимости в `run/mods/` с проверкой sha1+sha512.
5. Записать `mods-index.json`, обновить кэш UI.

Шаги идемпотентны: повторный запуск не дублирует файлы и не портит манифест.

### 5.5 Управление

- **Модпаки**: `.mrpack` → читается `modrinth.index.json`, ставятся указанные `minecraft` и `fabric-loader`, затем все `files[]` по хешам, затем `overrides/`. Пути вида `resourcepacks/…` сохраняются как есть.
- **Обновления**: хеш установленного файла против API → «устарело / нет на диске / чужой файл», кнопка «обновить все». Отдельно — проверка новой версии Fabric-лоадера.
- **Выключить без удаления**: переименование `X.jar` ↔ `X.jar.disabled` (так делают все лаунчеры, loader их игнорирует).
- **Проверка до запуска**: не хватает обязательной зависимости или есть `incompatible` → игру не запускаем, показываем список причин. Лучше объяснённая ошибка, чем краш меню.

## 6. Промо CozyPOLIT

Удалённый файл `cozypolit.json` в репозитории `sharrrrra1/CozyLauncher`, читается через `raw.githubusercontent.com` (настоящий TLS, домен не нужен, домен для этого проекта и не планируется).

Схема (всё валидируется по строгим типам, лишнее отбрасывается):

```json
{
  "schema": 1,
  "status": "closed",
  "title": "CozyPOLIT",
  "text": "Политический сервер: города, экономика, парламент, осады",
  "features": ["Города и нации (Towny)", "11 профессий", "Осады городов"],
  "server": { "mcVersion": "1.21.4", "address": "", "port": 25565 },
  "updatedAt": "2026-11-08"
}
```

- `status: "closed"` → карточка «открытие скоро» с реальными фичами; кнопки запуска нет.
- `status: "open"` → появляется кнопка **«Играть на CozyPOLIT»**: проверяет наличие 1.21.4 (это ядро сервера — Paper 1.21.4 build 232), при отсутствии предлагает установить, затем запускает с `--server <address> --port <port>`.
- `address` принимает только hostname или IPv4 из разрешённого алфавита и порт 1–65535; всё остальное — блок кнопки с понятной причиной. Аргументы попадают в `spawn` массивом, без оболочки, поэтому инъекция команд невозможна по конструкции.
- Офлайн/ошибка сети → последний кэш, а при пустом кэше — встроенный статичный блок из FEATURES.md. Промо не должно уметь ломать запуск игры.
- Смена адреса или открытие сервера правит только JSON в репозитории: переустанавливать лаунчер не нужно.

## 7. Автообновления лаунчера

- Зависимость `electron-updater` (проверено: `6.8.11` ставится) — в **`dependencies`**, не в dev: в собранном приложении его просто не будет, если положить неправильно.
- В build-конфиг: `publish: { provider: "github", owner: "sharrrrra1", repo: "CozyLauncher" }`. Тег релиза — `v<version>`; версия в `package.json` поднимается до `1.1.0` перед первым релизом.
- Поведение: проверка при старте (не чаще раза в 24 часа + кнопка «проверить вручную»), `autoDownload: false` → спрашиваем пользователя → скачиваем с прогрессом → `quitAndInstall` по явной кнопке. Никакой тихой подмены исполняемого файла без согласия.
- Обновляется **NSIS**-сборка. Портативный `.exe` самообновлением не управляет физически — ему показываем ссылку на новый файл; это ограничение формата, а не недоделка.
- Публикация требует `GITHUB_TOKEN` на время `npm run dist` (electron-builder выкладывает релиз и `latest.yml` сам). `gh` CLI в системе отсутствует, и это не нужно.
- Обновление не должно конфликтовать с single-instance lock: перед установкой приложение корректно закрывает окно и освобождает блокировку.

## 8. Безопасность, приватность и честные ограничения

- **«Без вирусов» гарантировать нельзя.** Ни один источник не даёт такой гарантии, поэтому в UI формулировка честная: «моды берутся только с Modrinth, файлы сверяются по хешу». Никаких сторонних зеркал и «обходов» в пути загрузки.
- **Моды — это чужой код с доступом к файлам и аккаунту.** Это неотключаемое свойство Minecraft-модов, и лаунчер обязан об этом говорить прямо, а не создавать ложное ощущение защиты от вирусов. Защита реальная и ограниченная: официальный API, сверка двух хешей, никакого автоматического скачивания и запуска того, что пользователь не подтвердил.
- **Защита от обхода путей.** `files[].path` из `.mrpack` и записи `overrides/` нормализуются и обязаны резолвиться строго внутри run-папки; `..`, абсолютные пути и симлинки отбрасываются (zip-slip). Проверяется тестом, а не на глаз.
- **Секретов в проекте нет и не появится.** Никаких API-ключей в коде и в `settings.json`: CurseForge не включён именно поэтому. Microsoft client id остаётся публичным (это нормально по их модели OAuth), токенты — как сейчас, через `safeStorage`. `GITHUB_TOKEN` живёт только в переменных окружения на время сборки.
- **Неподписанные сборки.** Windows SmartScreen будет предупреждать при первой загрузке установщика, и антивирусы иногда блокируют тихую установку неподписанного NSIS. Принимаем осознанно; лечится OV-сертификатом позже без смены архитектуры. Обязанность на релизе: опубликовать `SHA256SUMS.txt` рядом и инструкцию «как снять предупреждение».
- **Логи.** В `logs/` не пишутся токены и содержимое промо-запросов; путь run-папки и версии — пишутся.
- **Не трогаем чужое.** Существующие `.minecraft`-данные, ванильные версии и текущий UI расширяются, а не перезаписываются.

## 10. Тестирование

Автоматические (в `tests/*.test.ts`, текущая база — 15 тестов, `tsx --test`):

1. Синтез Fabric-профиля: `mainClass`, наличие `fabric-loader` и `intermediary` в библиотеках (тех, которых нет в `launcherMeta`), отсутствие дубликатов, корректный `inheritsFrom`.
2. Разрешение версии с родителем: слияние полей, глубина, цикл → ошибка.
3. Замыкание зависимостей: `required` рекурсивно, `optional` не тянется, `incompatible` блокирует, цикл и потолок по количеству/размеру.
4. Валидация путей `.mrpack` и `overrides/`: `../`, абсолютный путь, обратная косая черта — всё отклоняется.
5. Сверка sha512: правильный хеш проходит, подменённый — нет.
6. Валидация `cozypolit.json`: схемы, адрес/порт, неизвестный `status`.
7. Идентификаторы: `safeId` принимает синтезированные, отклоняет чужие.
8. Команда запуска: `--server/--port` появляются ровно один раз и только при валидном адресе.

Ручная проверка, которую выполняет агент сам:

## 13. Что нужно от владельца проекта

1. Создать и передать `GITHUB_TOKEN` с правом `repo` на `sharrrrra1/CozyLauncher` — для выкладки релиза (только переменная окружения на время сборки, в репозиторий не попадает).
2. Когда сервер откроется — поменять `status` на `"open"` и вписать `address` в `cozypolit.json`. Правка кода не потребуется.
3. Согласиться, что на неподписанной сборке Windows показывает предупреждение при первой установке.

## 14. Состояние репозитория

`C:\Users\home\Desktop\cozylauncher` **не является git-репозиторием** (проверено: `git rev-parse` → `fatal: not a git repository`), поэтому дизайн-документ лежит файлом и не закоммичен. Инициализация git и первая фиксация состояния — отдельное решение владельца, в объём этой spec не входит; для публикации релизов git и не требуется (electron-builder работает с GitHub Releases по токену).
